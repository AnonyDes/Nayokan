Developer handoff

A single-document overview of everything a development team needs to build the Nayokan Admin — routes, components, workflows, permissions, accessibility and its relationship to the public site.

Nayokan Admin · v0.1 · September 2026

The operating layer behind Nayokan's digital ecosystem.

Nayokan Admin is the institutional content, programme and impact-governance platform. It is a separate product from the public nayokan.cm site. Everything published on the public site is authored, verified and approved here first. This document is the blueprint for building it.

§ 02 · Components
Reusable admin components
Every screen is built from this component set. See design-system.html for the visual specs and states.html for state coverage.

Application shell: ax-app · ax-sidebar · ax-topbar · ax-workspace. Sidebar is 248px, collapsible on tablet, hidden on mobile with a hamburger topbar. Topbar height is 56px fixed.

Layout primitives: ax-page (default), ax-page--wide (no max width), ax-page--narrow (1120px). ax-page__head gives every screen a consistent title, eyebrow, lede and action group.

Data display: ax-panel · ax-stat · ax-table (with ax-toolbar, ax-tabs, ax-filter, ax-inline-search, ax-pagination).

Status vocabulary: ax-pill--{published, draft, review, needs, rejected, scheduled, archived, verified, active, expired, closing, upcoming, info, dark, neutral}. Every pill combines colour, label and dot — never colour alone.

Forms: ax-field + ax-input/ax-textarea/ax-select, ax-input__prefix, ax-toggle, ax-radio-group, ax-form-row (two-column label + body layout).

Feedback: ax-notice--{warn, danger, success, info, soft} · ax-modal for confirmations · ax-empty, ax-skeleton for empty and loading.

World tags: ax-world--{vti, sc, vc, hos} · always prefixed with the numbered world (01…04) in monospace.

§ 03 · Workflows
Publishing & verification workflows
Two chained workflows govern everything: the editorial publishing chain, and the impact verification chain. They are intentionally strict.

Editorial publishing chain

Draft → Submitted → In review → (Approved | Changes requested) → Scheduled → Published. Applies to Article, Page, Story, Programme, Opportunity, Person, Mentor, Partner, Property. Every state transition is written to AuditEntry with actor, timestamp and diff.

Publish is blocked if any of these preflight fields is missing: cover media, SEO title, SEO description, alt text on all inline media, and (for programmes) application deadline.

Impact verification chain

Drafted → Evidence attached → Verified → Approved → Public toggle. The Public boolean on ImpactMetric can only be set to true if the metric has passed Verified and Approved. Attempting to set public on a lower state must be rejected server-side with a ContentGovernanceError.

Evidence is append-only. Records cannot be edited after creation — corrections require a new evidence record superseding the old one, with an explicit link.

Review queue

Items enter the queue when submitted. They stay assigned to a single reviewer at a time. Items older than 72h are surfaced to leadership and can be reassigned.

§ 04 · Permissions
Roles & enforcement
Six roles with progressive access. See roles-permissions.html for the full matrix.

Roles: Super Admin · Content Editor · Programme Manager · Communications · Impact Manager · Reviewer.

Enforcement: Every route and API endpoint checks the caller's role against a policy map. UI permissions are advisory — the server is the source of truth. Actions marked "dangerous" (user disable, role change, integration edit, decommission) require dual approval from a second Super Admin before they execute.

2FA: Required for every admin account. No exceptions.

Sessions: 60 minute inactivity timeout. Autosave preserves drafts across sign-outs.

§ 05 · Public site
Relationship to the public Nayokan website
The admin owns content. The public site consumes it. They are separate deployments with a defined contract.

The public site (nayokan.cm) reads content from the CMS via a versioned content API. Only entities with public = true AND status = 'published' are served.

Preview: Every content object exposes a signed preview URL that renders it exactly as it would appear publicly. Preview URLs are prefixed preview.nayokan.cm/* and clearly badged PREVIEW · NOT LIVE.

Caching: Publishing writes to the CMS and invalidates the public-site cache within 60 seconds. Unpublishing removes from the cache immediately.

Scheduled publishing: A background job sweeps every 5 minutes for content whose scheduled_at has passed and moves it to Published.

§ 06 · Accessibility
Accessibility baseline
Target WCAG 2.2 AA. The admin is a working tool for institutional staff — accessibility is non-negotiable.
Keyboard navigation. Every interactive element is reachable by Tab. ⌘K/Ctrl K opens global search from anywhere.
Visible focus rings. 2px green outline with 2px offset on :focus-visible.
Never colour alone. Every status pill combines colour + label + dot. Every warning combines colour + icon + text.
Labels & aria. Every form field has a visible label. Icons that stand alone as buttons carry aria-label.
Alt text is required. Media cannot be attached to published content without alt text.
Reduced motion. Skeletons and transitions honour prefers-reduced-motion.
Contrast. Body text on workspace = 4.6 : 1. Pill text on tint = 4.5 : 1. Green on ink = 4.7 : 1.

§ 08 · Quality
Institutional quality test
The design meets the standard when every one of these questions can be answered "yes" without qualification.
Could a Nayokan employee use this without knowing how to code?
Could a communications employee publish an article end-to-end?
Could a programme manager manage applications from intake to decision?
Could an impact manager verify a metric before it appears publicly?
Could leadership approve content and see exactly what will publish?
Could an administrator control user permissions safely?
Could Nayokan update the homepage without a developer?
Could the team see exactly what is live on the public website?
Could an administrator recover an accidental content change?
Could the system prevent unverified information from being published as verified?
